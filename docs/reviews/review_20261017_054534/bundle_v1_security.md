## Findings

- [C][35] src/zmole/MoleBridge/MoleBridge.swift:314 — stdin 管道写入无任何错误与 SIGPIPE 处理，子进程先退出时可能以 SIGPIPE 杀掉整个 app — 证据：`DispatchQueue.global(qos: .utility).async { [stdinPipe, stdin] in … stdinPipe.fileHandleForWriting.write(stdin) … closeFile() }`（:312-317）为唯一 stdin 写点，写入时机与子进程退出/取消/超时（:353 terminateProcessGroup）存在竞态；全仓无 `signal(SIGPIPE, SIG_IGN)` 或 `F_SETNOSIGPIPE`（rg 证实）；macOS 上对无读端管道 `write(2)` 默认发送 SIGPIPE 终止进程（Foundation 不代为忽略；显式设置 `F_SETNOSIGPIPE` 才转为 EPIPE，Apple 论坛 thread/690382 明确说明），未忽略时 NSFileHandle 写失败还会抛 Swift 无法捕获的 `NSFileHandleOperationException` — 修复：进程启动早期设 `signal(SIGPIPE, SIG_IGN)`，stdin 写改为可抛错 API 并捕获，例如 `do { try stdinPipe.fileHandleForWriting.write(contentsOf: stdin) } catch { /* child already gone */ }`，或在 `MoleProcessRunner.init` 对写端 fd 执行 `fcntl(fd, F_SETNOSIGPIPE, 1)`。
- [M][60] src/zmole/MoleBridge/MoleBridge.swift:202 — 捆绑 mole 子进程继承完整父环境，`MOLE_*` 环境变量可改变删除语义而 GUI 未设置/净化 — 证据：`MoleProcessRunner.init`（:202-213）只设 executableURL/arguments/cwd/三个标准流，从不设 `process.environment`；而捆绑 CLI 消费环境变量：`docs/blueprint/architecture.md:18` 记录 `MOLE_DELETE_MODE=trash` 控制 installer 删除方式，`tests/integration/clean_trash_test.sh` 用 `MOLE_TRASH_DIR` 重定向废纸篓、`tests/integration/installer_interface_test.sh` 用 `MOLE_INSTALLER_SCAN_ROOT`/`MOLE_TEST_TRASH_DIR` 重定向扫描根与删除目标（即生产脚本按环境变量改变行为）；GUI 会话环境可被同用户进程经 `launchctl setenv` 持久化注入，使之后启动的清理 app 把删除改为 permanent 或重定向到指定目录 — 修复：为 mole 构造显式最小环境（PATH/HOME/LANG/TMPDIR + 明确设定 `MOLE_DELETE_MODE=trash` 等期望值），不直接继承 `ProcessInfo.processInfo.environment` 中的 `MOLE_*`。

- [Info][15] src/zmole/MoleBridge/MoleBridge.swift:358 — `kill(-pid)` 前仅以 `process.isRunning` 判定存在 pid 重用竞态 — 证据：`terminateProcessGroup` 取 `process.processIdentifier` 后 `guard pid > 0, process.isRunning`，随即 `kill(-pid, SIGTERM)`（:353-365）；若子进程恰在判定与 syscall 之间退出且 pid 被回收为新的进程组组长，信号会发错组（窗口微秒级，macOS 顺序分配 pid，实际概率极低；回收后组通常已空返回 ESRCH） — 修复：`finish()` 已置位时直接返回，并在 kill 前复核 `getpgid(pid) == pid` 且进程未标记 finished；如需彻底消除竞态，取消时记录 pgid 而非 pid。
